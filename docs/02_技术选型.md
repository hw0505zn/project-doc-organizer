# 02 · 技术选型

## 一、PDF 解析

选 `pdfplumber`，不选 `pymupdf` / `PyPDF2` / `camelot`，因为：工程资料表格多，`pdfplumber` 有表格提取 + 可视化调试，便于核对抽取位置；`pymupdf` 虽快但许可是 AGPL v3（商业闭源需买授权），`PyPDF2` 能力弱，`camelot` 只攻表格。代价：`pdfplumber` 无 OCR，扫描件交给 OCR 步骤；速度偏慢。

## 二、Word 解析

选 `python-docx`，因为：官方主流且稳定。注意它只管 `.docx`（Word 2007+），老的 `.doc` 不支持——需在需求/说明里限定输入格式，或对老文件预处理转 docx。

## 三、Excel 解析

选 `openpyxl`，因为：官方主流，管 `.xlsx`/`.xlsm`。注意不支持老 `.xls`；且"默认不防 XML 炸弹"——若资料来源不可信需额外校验。

## 四、OCR

选 `PaddleOCR`（轻量备选 `RapidOCR`），不选 `Tesseract` / `EasyOCR`，因为：工程扫描件多、精度优先，`PaddleOCR` 精度最高一档；`RapidOCR` 同样高且更轻量、部署简单，可作轻量备选。`Tesseract` 最快最轻但官方测试丢过金额小数点（自报置信度 93\~96%，不可全信），`EasyOCR` 依赖 PyTorch 较大。

> 结论模板（事实核对原话）：\*\*"OCR 不是一个问题，是三个问题"\*\* —— 检测 + 识别 + 解析，没有哪个库把三件都做好，金额类字段仍需二次校验。
> \*\*JPG / PNG 图片直接走本 OCR 链路\*\*：`pdfplumber` 只处理 PDF / 文本，图片不进 pdfplumber，由 OCR 先转文本再抽取。

## 五、界面框架

选 `Streamlit`，因为：课程指定、上手快、天然适配数据应用。`st.file\_uploader` 单文件上限 200MB；上传对象是 `io.BytesIO` 子类 → **`parse.py` 必须能吃"文件对象"而不只是"文件路径"**（这条反推 M3-1 的接口设计）。

## 六、LLM 模型

选 `deepseek-flash`（复杂/易错字段升级 `deepseek-v4-pro`），不选已退役的 `deepseek-chat` / `deepseek-reasoner`（2026-07-24 退役）。`flash` 快且便宜，适合批量 50 份字段抽取控成本；`pro` 精度更高，用于难字段兜底。注意思考模式默认开启。

## 七、⚠️ 我承认的局限

* `pdfplumber` 不处理图片、也不提供 OCR：JPG / PNG 图片与扫描件必须走"先 OCR 转文本再抽取"的链路；老 `.doc` / `.xls` 格式不支持，需限定输入格式或预处理；
* OCR 没有"全能库"：检测 / 识别 / 解析三件事要分开权衡，金额类字段仍需二次校验（Tesseract 曾丢小数点）。

## 八、代价与取舍

* 为避开 AGPL v3 商用授权风险，选 `pdfplumber` 而非 `pymupdf`，代价是解析速度更慢、且必须额外接 OCR 链路；
* 为控批量成本，选 `deepseek-flash` 而非 `pro` 跑全部字段，代价是复杂字段准确率略低——以"flash 为主、pro 兜底难字段"平衡。
